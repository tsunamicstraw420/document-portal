  Section 5 — UFW Firewall Configuration
 UFW (Uncomplicated Firewall) was configured with a strict deny-incoming, allow-outgoing policy.


 Commands Executed
            ufw default deny incoming ufw default allow outgoing ufw allow 22/tcp ufw allow out
            443/tcp ufw allow out 9443/tcp ufw enable


 Firewall Rules Applied

 Rule                          Direction               Action     Purpose

 Default incoming              INBOUND                 DENY       Blocks all unsolicited inbound connections

 Default outgoing              OUTBOUND                ALLOW      Bots can connect outbound freely

 Port 22/tcp                   INBOUND                 ALLOW      SSH access

 Port 443/tcp                  OUTBOUND                ALLOW      HTTPS + standard WSS WebSocket

 Port 9443/tcp                 OUTBOUND                ALLOW      Binance WebSocket stream endpoint

  NOTE: WHY PORT 9443: Binance uses port 9443 for its WebSocket market data streams
  (wss://stream.binance.com:9443/ws/). This must be explicitly allowed outbound for trading bots.

 Verification
            ufw status verbose

 Status: active, enabled on system startup


  Section 6 — Fail2Ban Configuration
 Fail2Ban protects SSH from brute-force attacks by banning IPs after repeated failed login attempts.

 Configuration File
 File created: /etc/fail2ban/jail.d/sshd.conf
            [sshd] enabled = true port = 22 filter = sshd logpath = /var/log/auth.log maxretry = 3
            findtime = 600 bantime = 3600


 Settings Explained

 Setting                     Value               Meaning

 maxretry                    3                   Ban after 3 failed login attempts

 findtime                    600                 Count failures within a 10-minute window

 bantime                     3600                Ban offending IP for 1 hour


 Commands
            systemctl enable fail2ban systemctl restart fail2ban

 Status: active (running), enabled on system startup. Main PID confirmed running as fail2ban-server


  Section 7 — WebSocket & TCP Kernel Tuning
 The Linux kernel was tuned for high-concurrency WebSocket connections required by trading bots that
 maintain persistent connections to exchange APIs.

 Configuration — appended to /etc/sysctl.conf
            net.core.somaxconn = 65535 net.ipv4.tcp_max_syn_backlog = 65535
            net.ipv4.tcp_keepalive_time = 60 net.ipv4.tcp_keepalive_intvl = 10
            net.ipv4.tcp_keepalive_probes = 6 net.ipv4.tcp_fin_timeout = 15
            net.ipv4.ip_local_port_range = 1024 65535


 Settings Explained

 Parameter                                        Value              Purpose

 net.core.somaxconn                               65535              Maximum socket connection backlog

 net.ipv4.tcp_max_syn_backlog                     65535              Maximum pending TCP connections

 net.ipv4.tcp_keepalive_time                      60                 Send keepalive probe after 60s idle — prevents WebSocket drops

 net.ipv4.tcp_keepalive_intvl                     10                 Retry keepalive every 10 seconds

 net.ipv4.tcp_keepalive_probes                    6                  Drop connection after 6 missed keepalives (60s total)

 net.ipv4.tcp_fin_timeout                         15                 Release closed connections faster (default is 60s)

 net.ipv4.ip_local_port_range                     1024–65535         Maximum available outbound ports for concurrent connections

  Section 10 — Next Steps
 The VPS is now ready for bot deployment. Recommended workflow:

     • Create a non-root deploy user with SSH key authentication
     • Upload bot code via SCP or git clone from repository
     • Create docker-compose.yml with bot services
     • Store API keys in a .env file (never hardcode in source)
           docker compose up -d # start all services docker compose logs -f # monitor live output
