AI_bots — House Rules

This folder holds all of Eddie's ongoing projects, each in its own subfolder. New projects get new subfolders. Claude_and_AI_Docs/ holds finished general documentation.

AI video / animation prompting — ANY project. Before writing any AI video/clip prompt (Kling, Runway, image-to-video, etc.), read Claude_and_AI_Docs/VIDEO_PROMPTING_GUIDE.md. It is the reusable playbook for making generated clips actually move: ground the keyframe, spell out the full beat-by-beat motion arc with foot-to-floor contact, use a START+END keyframe pair to force locomotion (a leaping/mid-stride pose held static "flies in place"), paste a camera move from the library, and put anti-float terms in the negative-prompt field. Terse motion prompts freeze or hover and waste paid credits.

AI image / video prompting — ANY project. For any image or video prompt work (writing, fixing, picking a model, character sheets, camera moves, chaining clips), also load the visual-prompting skill. Project rules win: the project's own CLAUDE.md and proven prompt formula come first, then VIDEO_PROMPTING_GUIDE.md for clips, then the skill fills the gaps.

READ THIS FIRST — every session, before the first tool call

Cowork does not auto-load this file the way terminal Claude Code does. So:

  1. Read this file.
  2. Read the CLAUDE.md in the specific project subfolder you're working in, if one exists.
  3. Only then start work.

If you are reading this after already doing work, stop and check what you did against the rules below before continuing.

The 12 rules

1. Verify before handing back. Never hand Eddie QA. Run the check yourself and report the actual number, path, or output. "Should work," "looks right," and "I've updated it" are not verification. If you wrote a file, read it back. If you edited code, run it. If you counted something, print the count.

2. Name your source for every factual claim. "The log shows X" is fine. "X is happening" without naming what you checked is forbidden when X is verifiable. The phrasing forces the discipline.

3. Live state beats written claims — including this file. Docs go stale. Before asserting where something runs, what version is deployed, or what a folder contains: go look. ls, git log, docker ps, read the file.

4. Copy the working example. Never design a new approach. If this project has done this kind of operation before, find how it was done and do it that way. Read the prior script or folder before forming a theory. Improvising a "better" method is the most expensive recurring mistake across these projects.

5. Empirical test beats documentation reading. "Does this API do X?" → write a 30-line probe and run it. WebFetch summaries, READMEs, and your own prior conclusions are not the live system.

6. Deliverables only — no intermediate artifacts. Asked for a PDF? Write the PDF, delete the generator. If you needed a gen_*.py, a probe, or a scratch .md, clean it up before saying you're done. One output per ask. If unsure whether to keep an intermediate file, ask before leaving it behind.

7. Never write files with shell heredocs. Use the Write/Edit tools, or write in the cloud container and commit the file across. A broken heredoc silently appended EOF and a raw cat line into zc_trading/CLAUDE.md and sat there undetected. Heredocs fail silently; tools don't.

8. Never modify .env, credentials, or key files. .env, Accounts_info.rtf, _creds.rtf, .key. Read only when required, never write, never echo contents into chat or logs.

9. Don't make Eddie sit and watch. He multitasks. Any approach that pins his machine or needs supervision is a failed approach even if it eventually works. Route order: MCP connector → reconnect the connector → device_bash/Bash → a .command file he double-clicks once → Claude in Chrome (last resort; state which of the prior routes you tested and the exact error each gave).

10. Don't ask for clicks until every other route has been tested. Not "I think this is blocked" — tested, with the error message in hand.

11. Fix the cause, not the instance. When something goes wrong, write the working method down so the next session inherits it instead of rediscovering it. That means editing the relevant CLAUDE.md, not just fixing the file in front of you.

12. Scope discipline. Don't refactor, rename, reorganize, or "clean up" anything that wasn't asked for. Don't average two existing patterns — pick one and follow it.

Self-check before saying "done"

Cowork runs in the cloud and cannot execute the .claude/ hook scripts on this Mac. There is no automated gate here. This checklist is the gate. Run it explicitly, in writing, before every final response that involved tool calls:

1. Did I actually verify each factual claim, and name the source?     yes / no
2. Did I read back every file I wrote or edited?                      yes / no
3. Did I delete every intermediate/scratch file I created?            yes / no
4. Did I do anything that wasn't asked for?                           yes / no
5. Is there a check I skipped and am hoping is fine?                  yes / no

If #5 is yes, go run it. That question is the one that catches the real failures.
