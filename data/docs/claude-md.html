AI_bots — House Rules

This folder holds all of Eddie's ongoing projects, each in its own subfolder. New projects get new subfolders. Claude_and_AI_Docs/ holds finished general documentation.

AI video / animation prompting — ANY project. Before writing any AI video/clip prompt (Kling, Runway, image-to-video, etc.), read Claude_and_AI_Docs/VIDEO_PROMPTING_GUIDE.md. It is the reusable playbook for making generated clips actually move: ground the keyframe, spell out the full beat-by-beat motion arc with foot-to-floor contact, use a START+END keyframe pair to force locomotion (a leaping/mid-stride pose held static "flies in place"), paste a camera move from the library, and put anti-float terms in the negative-prompt field. Terse motion prompts freeze or hover and waste paid credits.

On-screen text / motion graphics — ANY project. Before putting ANY words on a video (ads, Shorts, Reels, trailers, explainers, captions-as-design), read Claude_and_AI_Docs/Motion_Text_Playbook.html. It's the method Eddie called "amazing" on course ad 03: the text is part of the story's concept (decide that first), never on a face (map faces with Apple Vision, place text in the empty bands), nothing appears without an animated entrance, each genre/mood gets its own type, and every slam gets a sound hit. Exact spring/timing values and the reference Remotion build (Magnific_clone/studio/tools/explainer/src/SameFace.jsx) are in it. Static captions faded on and off = rejected as "basic". Copy the playbook's components instead of improvising.

AI image / video prompting — ANY project. For any image or video prompt work (writing, fixing, picking a model, character sheets, camera moves, chaining clips), also load the visual-prompting skill. Project rules win: the project's own CLAUDE.md and proven prompt formula come first, then VIDEO_PROMPTING_GUIDE.md for clips, then the skill fills the gaps.

READ THIS FIRST — every session, before the first tool call

Cowork does not auto-load this file the way terminal Claude Code does. So:

  1. Read this file.
  2. Read the CLAUDE.md in the specific project subfolder you're working in, if one exists.
  3. Only then start work.

If you are reading this after already doing work, stop and check what you did against the rules below before continuing.

The 12 rules

1. Verify before handing back. Never hand Eddie QA. Run the check yourself and report the actual number, path, or output. "Should work," "looks right," and "I've updated it" are not verification. If you wrote a file, read it back. If you edited code, run it. If you counted something, print the count.

2. Name your source for every factual claim. "The log shows X" is fine. "X is happening" without naming what you checked is forbidden when X is verifiable. The phrasing forces the discipline.

3. Live state beats written claims — including this file. Docs go stale. Before asserting where something runs, what version is deployed, or what a folder contains: go look. ls, git log, docker ps, read the file.

4. Copy the working example. Never design a new approach. If this project has done this kind of operation before, find how it was done and do it that way. Read the prior script or folder before forming a theory. Improvising a "better" method is the most expensive recurring mistake across these projects.

5. Empirical test beats documentation reading. "Does this API do X?" → write a 30-line probe and run it. WebFetch summaries, READMEs, and your own prior conclusions are not the live system.

6. Deliverables only — no intermediate artifacts. Asked for a PDF? Write the PDF, delete the generator. If you needed a gen_*.py, a probe, or a scratch .md, clean it up before saying you're done. One output per ask. If unsure whether to keep an intermediate file, ask before leaving it behind.

7. Never write files with shell heredocs. Use the Write/Edit tools, or write in the cloud container and commit the file across. A broken heredoc silently appended EOF and a raw cat line into zc_trading/CLAUDE.md and sat there undetected. Heredocs fail silently; tools don't.

8. Never modify .env, credentials, or key files. .env, Accounts_info.rtf, _creds.rtf, .key. Read only when required, never write, never echo contents into chat or logs.

9. Don't make Eddie sit and watch. He multitasks. Any approach that pins his machine or needs supervision is a failed approach even if it eventually works. Route order: MCP connector → reconnect the connector → device_bash/Bash → a .command file he double-clicks once → Claude in Chrome (last resort; state which of the prior routes you tested and the exact error each gave).

10. Don't ask for clicks until every other route has been tested. Not "I think this is blocked" — tested, with the error message in hand.

11. Fix the cause, not the instance. When something goes wrong, write the working method down so the next session inherits it instead of rediscovering it. That means editing the relevant CLAUDE.md, not just fixing the file in front of you.

12. Scope discipline. Don't refactor, rename, reorganize, or "clean up" anything that wasn't asked for. Don't average two existing patterns — pick one and follow it.

Self-check before saying "done"

Cowork runs in the cloud and cannot execute the .claude/ hook scripts on this Mac. There is no automated gate here. This checklist is the gate. Run it explicitly, in writing, before every final response that involved tool calls:

1. Did I actually verify each factual claim, and name the source?     yes / no
2. Did I read back every file I wrote or edited?                      yes / no
3. Did I delete every intermediate/scratch file I created?            yes / no
4. Did I do anything that wasn't asked for?                           yes / no
5. Is there a check I skipped and am hoping is fine?                  yes / no

If #5 is yes, go run it. That question is the one that catches the real failures.

A. Money: never spend without a clear yes

  • Every paid run needs Eddie's yes for that spend, in dollars, even cents. Give the customer

price and the owner cost (customer ÷ 2.5). "Research" means free reading. Never fire paid jobs in parallel without a yes: a stop can't recall jobs already sent. [10-16]

  • First ask whether Eddie already has it, or makes it himself for free (Gemini, his own tools).

Never pitch spending on something he just showed he does himself. [10-24: thumbnails]

  • Never generate what already exists. Take finished assets from the connected service's own

logged-in UI first (e.g. Magnific characters via pikaso.cdnpk.net signed URLs in Chrome). Rebuild only when the finished asset truly can't be reached. [09-21]

  • One paid attempt per model. If a schema-valid paid call fails, STOP: read the model's

docs page, compare against its exact example body, and run a free check before paying again. Changing one guessed parameter and re-paying is not debugging. [09-18]

  • Before ANY paid batch, run ONE item and check every property the deliverable needs (shape,

pixel size, likeness, content). Picture-EDIT models copy the source picture's shape; for a fixed output shape use text-to-image with the character in refImageUrls. Read back every URL and parameter before sending. [10-22]

  • Test a new feature first on a top model customers actually pick for that job, so a failure

means the feature is broken, not the model weak. Cheap models only after it's proven. [10-06]

  • A full render is the LAST step, run once. First print the changed lines' word times next to

their clicks (free) and fix gaps over 0.5 s, then render only the changed section (--frames=a-b), then the whole video. Say up front how many renders a fix needs. [10-21]

  • solorender pricing: price = real cost × 2.5. Every cost drop goes to the customer; never call

it extra margin. Check price_adjustments / /api/models/prices before describing prices. [10-16]

  • A price Eddie calls absurd is not a budget. Never quote it back as a limit ("under your $30").

Keep his exact meaning when writing his words into a rule. [10-22]

B. Look at every result before Eddie sees it (he is not the QA)

  • A test passes only after I have LOOKED at every output: a frame strip (start, middle, end)

of every clip, every picture at readable size, voice length and loudness. Check it against what was promised. Report "plumbing works" and "looks right" separately. [10-11]

  • QA the way the customer sees it: the whole result page and the FINISHED film, start to end,

against the brief. Does the action match the input? Does anyone leave and re-enter? Is every cut a real change of angle, not a zoom? Any one of these = FAIL, not "small flaw". [10-14]

  • QA a picture against its STORY, not its parts. Does it show the moment the script describes

(dodging = no laser touches him)? Check where hazards, props and lines meet the character at full size. [10-22]

  • Read every picture the way a stranger would at a glance: what is the body showing, who is it

facing, could it read as rude, sexual or creepy (especially near children)? If so, don't send it. Never prompt poses like "on its back, belly up" near kids. [10-21]

  • Clip checklist (a frame strip is not enough on its own):
  • Camera moves: a push-in makes the subject AND background grow; a pull-back makes both shrink.

People the camera moves past must LEAVE the frame and stay gone. Background holding its size, or people riding along at the edges = faked move = FAIL. [10-18]

  • Hands: what is each hand touching, frame by frame? In prompts, name the exact prop ("both

hands on the computer keyboard") or avoid the action. [10-23]

  • Feet: a CLOSE-UP strip of the feet at 4+ frames a second, whole clip. Every step lands on the

surface, never past an edge, and the surface keeps its shape (no buckling where a foot lands). A tracking prompt must say the surface keeps going ahead of him. [10-23, 10-24]

  • Anything the model drew that wasn't in the start picture (a door, a prop, a person): check its

kind, size and direction against the script. If a crop removed a prop the action needs, make a new start picture that shows it. [10-22]

  • Cuts: trim every shot to an exact frame count, confirm real cut times with scene detection

(select='gt(scene,0.25)',showinfo) before adding crops/text/sound, and check a frame strip across every cut of the final file. [10-24]

  • Before paying, audit prompts for ambiguous motion words ("turn", "drop", "flip") and

voice/face mismatches. [10-11]

  • Speech checks: every Whisper pass uses vad_filter=True and reports no_speech_prob.

"Thank you" / "thanks for watching" on quiet audio is Whisper's stock hallucination, never proof of speech. Before any speech test, confirm the source clip actually has speech, and confirm a problem exists by a second check before building a fix. faster-whisper is installed: HF_HUB_OFFLINE=1 /usr/bin/python3 script.py WITHOUT -I (models small, small.en, base; see Podcast/Podcast/vps-pipeline/transcribe.py). Check spoken lines in every clip. [10-15, 10-23]

  • A voice cut into pieces is cut only inside a measured pause (silencedetect at −30 dB), with no extra

frames past the cut, and each cut point's loudness is measured (≥25 dB below speech). Whisper does NOT catch a doubled syllable: it heard "Included" once while Eddie heard "Inc… Included". [10-25]

  • Names and pronunciation are checked by ear, not Whisper (it spells what it guesses). Write a

name the way it should sound ("Solo render") if the voice slips. [10-21]

  • Lip sync / voice tests: use a silent, non-talking source clip and a voice about as long as

the clip; copy the provider's example settings (Runware: originalAudioVolume: 0). Before showing: Whisper the output (only the new words?), measure leftover original sound, and lay out mouth crops every 0.2 s against word timings. [10-16]

  • Before feeding a recording to a voice clone, listen-check it like a result. A file name

("clean", "final") proves nothing; Whisper proves words, not sound quality. [10-16]

  • A measurement can rule a claim out but can't prove a quality (a laugh, a style, a likeness).

No quality claim goes on a customer page until a person has seen or heard it. [10-06]

  • "I can't judge that" is never a hand-off to Eddie. Find the measurement that can. [10-16]
  • Every test that makes something ends with the result sent to Eddie via SendUserFile

(download URL results first), captioned with what was tested. Measurements go alongside, never instead. A batch gets the results or a contact sheet. [10-06]

Content Creator template & sound library — resolving "use the X template/macro"

Eddie downloaded the full contentcreatortemplates.com DaVinci Resolve library plus a sound sampler. From any chat (podcast episodes, etc.) he may say things like "use the Modern Titles Pack for the intro" or "grab the crt-effect macro". Resolve it yourself — don't make him hunt for files.

  • Template index: Content_Creator_Learn/Templates_Macros/DaVinci_Templates_Index.csv

— columns Category, Name, ID, Filename, Link. Match his words against Name (fuzzy is fine) or the numeric ID. If several match, list the candidates briefly and let him pick.

  • Pack file: Content_Creator_Learn/Templates_Macros/<Category>/<Filename> (a .zip).

Inside each: .setting/.drfx macros (+ Fonts/, Help/Tutorial.mp4). ~1,335 packs across 12 categories: Titles, Lower Thirds, Transitions, Effects, Generator, Infographics, Overlays, YouTube, Text, Logos, Intros, Motion Graphics. (Packs are hard-linked across the categories they belong to, so a pack may appear in more than one category folder.)

  • Sounds: Content_Creator_Learn/Sound_Effects/<Category>/<slug>.zip (~2,000-file sampler).
  • Visual browser: Content_Creator_Learn/Template_Sound_Gallery.html (also on his Desktop

as Template & Sound Gallery.html) — how he eyeballs/previews/likes them. Previews stream from the site's public storage; the downloaded packs are local and offline.

  • Install into Resolve: Content_Creator_Learn/Templates_Macros/install_to_davinci.command

unzips the macros into ~/Library/Application Support/Blackmagic Design/DaVinci Resolve/ Fusion/Templates/Edit/<cat>/ (Lower Thirds get their own bin under Titles). It skips the tutorial videos and fonts on purpose.

When he names one: confirm the match (Name + Category), give the exact zip path, then help him actually use it — extract the .setting/.drfx, get it into DaVinci, and customize it for that episode. The bundled Help/Tutorial.mp4 clips are auto-generated/sped-up and not worth surfacing; guide him directly instead.
