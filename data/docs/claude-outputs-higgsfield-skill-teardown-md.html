Reverse-Engineering the Higgsfield Skill — Teardown + Magnific/Kling Adaptation Plan

Source: github.com/higgsfield-ai/skills (v0.12.0, MIT license). Nine skills, cloned and read in full.

Part 1 — How the Higgsfield skill actually works

1.1 The core insight

Every one of the nine skills is a thin Markdown wrapper around one CLI binary (higgsfield). No skill talks to the API directly. From CLAUDE.md:

All skills route through one binary: the higgsfield CLI. Do not call api.higgsfield.ai directly with curl. The CLI handles auth, retries, polling, schema validation, and auto-uploads. Skipping it bypasses critical behavior.

So the "skill" contributes zero runtime code. It is pure instruction + knowledge: it tells the agent when to fire, which command to run, which model to pick, and how to present the result. The CLI does all the heavy lifting.

This is the single most important thing to internalize for your adaptation: a skill is a decision-making layer, not an execution layer. The execution layer (CLI for Higgsfield; MCP tools for Magnific/Kling) already exists.

Nine skills: generate (flagship), soul-id, product-photoshoot, brandkit, marketplace-cards, websites, video-explainer, youtube-thumbnail, game-generation.

1.3 The SKILL.md contract

Every SKILL.md follows the same skeleton. This is the reusable template:

Frontmatter (YAML) — four fields that matter:

  • name — the skill id.
  • description — a triggering block, not a summary. It packs literal user phrases ("generate an image", "animate this photo", "make a UGC video") so the agent knows when to load the skill, plus explicit Chain with… and NOT for… lines to route away misfires. This is the highest-leverage part of the whole file — it's how the agent decides to use the skill at all.
  • argument-hint — the shape of a slash-command invocation.
  • allowed-tools: Bash — the skill only needs a shell (because everything is a CLI call).

Body, in a fixed order:

  1. Step 0 — Bootstrap. Check the binary is installed and authed; if not, install/auth. Runs before anything else.
  2. UX Rules. Global rules that apply on every turn: be concise, no raw IDs/JSON in chat, detect language, don't batch questions, prefer the quality default, use one-shot --wait.
  3. Decision trees. The bulk of the file: a model-selection matrix ("cinematic still → Soul Cinema; logo → Recraft; default → GPT Image 2"), mode selection, target detection, and routing to other skills when out of scope.
  4. Command recipes. Copy-pasteable command shapes with real flags.
  5. Errors. Symptom → fix table.
  6. Reference pointers. See references/X.md for details.

1.4 The 300-line rule (context economy)

From CLAUDE.md:

Each SKILL.md should aim for under 300 lines… loaded into the agent's context whenever the skill triggers — every line costs latency and tokens. The test: if removing a section would NOT break the agent's ability to decide what to do next, it belongs in references/.

So SKILL.md holds only what's needed to decide the next action. Everything an agent needs once, after deciding — full flag tables, prompt galleries, troubleshooting trees, model catalogs — moves to references/*.md, loaded on demand. The flagship generate/SKILL.md is 325 lines; its 14 reference files add ~1,300 more that load only when relevant.

1.5 Source-of-truth discipline

The skill never hardcodes the model list as fact. It ships a references/model-catalog.md as an intent→command mapping, but repeatedly instructs: run higgsfield model list --json for the live catalog, higgsfield workflow list for workflows, higgsfield preset list for presets. The catalog in the repo is a routing hint; the CLI is the truth. This keeps the skill from rotting when the backend changes.

1.6 Skill chaining via return values

Skills compose through explicit outputs, not shared state:

  • soul-id trains a face → returns a reference_id.
  • generate consumes it via --soul-id <id>.
  • Rule: "Skills communicate through return values, not implicit state."

And a scope contract on every skill: Use when (triggers) / Chain (hand-offs) / NOT for (boundaries). This is what stops nine overlapping skills from stepping on each other.

1.7 Multi-agent portability

The same skill folder ships to Claude Code (~/.claude/skills/), Cursor (~/.cursor/plugins/), and Codex (~/.codex/plugins/) via three parallel manifests + an auto-detecting setup script. Each skill folder is fully self-contained — no ../ references — so any single skill can be installed standalone. CI enforces self-containment and version sync on every PR.

1.8 One-shot execution pattern

The command pattern to copy: higgsfield generate create <model> --prompt "…" [media flags] --wait. The --wait flag blocks until the job is terminal and prints the result URL itself — so the skill never writes polling loops. Media flags (--image, --start-image, --video) accept a local path (auto-uploaded) or a UUID (a prior job's output), which is what makes chaining (image → video) trivial.

Part 2 — Mapping onto Magnific / Kling

2.1 The one structural difference

Everything else — the frontmatter triggering block, UX rules, the model-selection decision tree, references split by the 300-line rule, chaining by return value, scope boundaries — transfers directly and unchanged. You are swapping the execution verbs, not the architecture.

2.2 Verb-by-verb translation

Bootstrap (Step 0). Higgsfield checks the binary + auth. Yours checks the connector is live and reads capabilities:

  • Magnific: account_profile / account_balance, then images_models_list, video_models_list.
  • Kling: who_am_i first (the server's own instructions require it), then query_membership_and_credits.

Generate an image.

  • Higgsfield: higgsfield generate create gpt_image_2 --prompt "…" --wait
  • Magnific: images_generate (then creations_wait on the returned identifier, then creations_show for inline preview)
  • Kling: text_to_image

Image → image / edit / upscale / restyle.

  • Magnific has the richest surface here: images_upscale, images_variations, images_expand, images_relight, images_retouch, images_remove_background, images_change_camera, images_to_svg. (This is Magnific's core strength — it's an editing/upscaling engine as much as a generator.)
  • Kling: image_to_image

Text → video / image → video.

  • Magnific: video_generate (chain by passing the image creation identifier, per the server's relay instructions — never the webUrl)
  • Kling: text_to_video, image_to_video, plus motion_control for driven motion

Audio. Magnific: audio_tts, audio_music_generate, audio_sfx_generate, audio_voice_change, audio_isolate. (Kling has no audio.)

3D. Magnific: models3d_generate, models3d_rig. (Direct analog to Higgsfield's multi_image_to_3d.)

Poll / retrieve. Magnific: creation_status, creations_wait, creations_get. Kling: query_tasks.

2.3 Two Magnific-specific rules the skill must encode

Read straight from the connector's own instructions — these are the equivalent of Higgsfield's "don't curl the API" rule:

  1. After any generation, call creations_show for inline preview, then creations_wait (1–8 ids per call) to confirm before replying. Never regenerate queued creations.
  2. When chaining image→video, pass the creation identifier (or the url from creations_get/creations_wait), never the webUrl. And for local input files, call creations_upload_show — the server can't read chat attachments.

Kling's equivalent house rules: call who_am_i first; every job is charged, so confirm intent before submitting (no trial jobs); map any alias words to canonical model/argument names before calling.

2.4 Model routing — the piece you'll customize most

Higgsfield's decision tree is its most valuable IP ("cinematic still → Soul Cinema, logo → Recraft, fast/cheap → Z Image, default → GPT Image 2"). Yours becomes a Magnific-vs-Kling + which-tool matrix, and — following Higgsfield's source-of-truth discipline — it should be built by reading images_models_list / video_models_list / who_am_i live, not hardcoded. A first-cut routing table:

BriefRoute
Upscale / enhance / "make this sharper / bigger"Magnific images_upscale (its flagship capability)
Edit an existing image (relight, retouch, expand, remove bg, restyle)Magnific image-edit family
General text-to-imageMagnific images_generate or Kling text_to_image — pick per model list
Vector / SVGMagnific images_to_svg / images_generate_svg
Driven / controlled motion videoKling motion_control
Straight text/image-to-videoKling text_to_video / image_to_video, or Magnific video_generate
Audio (TTS, music, SFX)Magnific audio family (Kling can't)
3D meshMagnific models3d_generate

2.5 What you get to drop entirely

Because the MCP layer replaces the CLI:

  • The setup script, the CLI installer, the OAuth bootstrap — gone. No install, no auth, no PATH.
  • Polling-loop code — gone. creations_wait / query_tasks are single tool calls.
  • The multi-agent manifests (.claude-plugin, .codex-plugin, .cursor-plugin) — only needed if you want to distribute the skill across agents. For a personal skill, one SKILL.md in your skills directory is enough.

Part 3 — A concrete skeleton for your skill

A single starter skill (media-generate) that mirrors Higgsfield's flagship but drives your MCP tools:

---
name: media-generate
description: |
  Generate and edit images, video, audio, and 3D via Magnific and Kling
  (both connected as MCP servers — no install, no auth).
  Use when: "generate an image", "make a video", "animate this photo",
  "upscale/enhance this", "relight/retouch/expand this image",
  "remove the background", "make a sound effect / music / voiceover",
  "text-to-video", "controlled motion", "create a 3D model".
  Routing: Magnific for upscaling, image editing, audio, and 3D;
  Kling for text/image-to-video and motion control; either for
  plain text-to-image (check the live model list).
  NOT for: brand systems, YouTube thumbnails, or website builds.
allowed-tools: mcp__Magnific__*, mcp__KlingAI__*
---

# Media Generate

## Step 0 — Capabilities
- Kling: call `who_am_i` first (required by the server), then check credits.
- Magnific: `account_profile`; read `images_models_list` / `video_models_list`
  for the LIVE model set. Never hardcode model names.

## UX Rules
1. Be concise. Show the rendered result (Magnific: `creations_show`), not raw ids/JSON.
2. Every job is charged — confirm intent, no trial runs, never regenerate a queued job.
3. Pick a sane default and ask one thing at a time only if genuinely missing.
4. Local input files → Magnific `creations_upload_show` (the server can't read chat attachments).

## Routing (verify against the live model list)
[the Part 2.4 table]

## Recipes
- Image:  images_generate → creations_wait → creations_show
- Upscale: images_upscale → creations_wait → creations_show
- Video (chain): pass the image CREATION IDENTIFIER (not webUrl) into video_generate
- Kling video: text_to_video / image_to_video → query_tasks
- Audio: audio_tts / audio_music_generate / audio_sfx_generate

## Errors
- Missing prompt → ask for it.
- Kling alias word → map to canonical model/arg name before calling.
- On timeout/failure → tell the user, ask before retrying (don't auto-resubmit).

## References (load on demand)
- references/magnific-editing.md — the full image-edit family + flags
- references/kling-motion.md — motion_control and driven-motion inputs
- references/routing.md — the full decision matrix

That's the whole pattern: the same architecture, with higgsfield generate create swapped for MCP tool calls and the install/auth machinery deleted.

Bottom line

The Higgsfield skill's real value isn't code — it's a disciplined instruction architecture: a trigger-packed description, a fixed body order (bootstrap → UX rules → decision tree → recipes → errors → references), the 300-line context-economy rule, live-source-of-truth over hardcoding, and composition by return value with explicit scope boundaries. All of that ports 1:1 to Magnific/Kling. The only thing you throw away is the part you never needed: the CLI install and auth, because your execution layer is already live in-session as MCP tools.
