Architecture

Components

Browser (Next.js client)
    │  (never sees provider or Stripe secret keys)
    ▼
Next.js server (App Router route handlers / server actions)
    ├── /api/generate ........ the metered spine: auth → reserve → call model → settle → store
    ├── /api/stripe/webhook .. the only place credits are added from payments (idempotent)
    └── auth, dashboards ..... Supabase Auth session
    │
    ├──► Supabase Postgres .... profiles, credit_wallets, credit_transactions (ledger),
    │                           generations, subscriptions, abuse_reports
    ├──► Supabase Storage ..... generated outputs (or Cloudflare R2)
    ├──► Model providers ...... OpenRouter (image+text), fal.ai, Replicate  [server-side only]
    └──► Stripe ............... subscriptions + one-time credit packs

The generation flow (the spine)

  1. Client POSTs { modelId, prompt, idempotencyKey } to /api/generate.
  2. Server authenticates the user (Supabase session).
  3. Look up the model + its credit cost in lib/models.ts.
  4. Moderate the prompt (Phase 5 — launch blocker). Block before spending.
  5. Insert a generations row (status reserved).
  6. Reserve the credits atomically (reserve_credits SQL fn) — fail with 402 if short.
  7. Call the provider server-side via an adapter.
  8. On success: moderate output, then settle the reservation, save the output URL,

set status succeeded. On any failure/timeout: release the reservation (user is never charged for a generation that didn't happen), set status failed.

  1. Return the output. Long video jobs use a queue + provider webhook instead of a blocking call.

The credit ledger (why it's designed this way)

  • credit_transactions is append-only and is the source of truth; credit_wallets.balance

is a cached integer that must always equal sum(amount) for the user.

  • Every mutation is one transaction. Reserve-then-settle guarantees a failed generation refunds

automatically. idempotency_key (unique) makes both generate retries and Stripe webhook retries safe no-ops.

  • A nightly reconciliation job should assert balance == sum(transactions) per wallet and alert

on drift.

Model routing

lib/models.ts maps a model id → provider, capability, wholesale cost, and credit cost. Provider adapters (Phase 3) share one interface call(model, input) → { url }. Adding a model is a data entry + (if a new provider) one adapter — never a rewrite. Because credit cost is a data field, a wholesale price change is a config edit.

Payments

Stripe is the source of truth for subscription state; the webhook mirrors it into subscriptions and is the only path that grants credits (keyed by Stripe event id). Tiers/packs → credit allowances live in lib/stripe.ts, in sync with docs/unit-economics.md.

Security + compliance

  • All provider/Stripe secret keys are server-side env only; every model call is proxied. (fal.ai

ToS forbids exposing its API to end users.)

  • Moderation (prompt + output) + an NCII/abuse report with a 48-hour takedown workflow

(abuse_reports) are required before public launch (TAKE IT DOWN Act).

  • Rate limiting + Stripe Radar to blunt abuse and chargebacks. RLS on all user tables.

Deployment

Vercel (Next.js) + Supabase (Postgres/Auth/Storage) + Stripe. Cloudflare R2 optional for cheaper media storage/egress. Add a queue (Inngest / QStash) when video jobs land in Phase 3.
