How the numbers were worked out: Google's live Cloud Run price page (us-central1), 25 Oct 2026. Always-on copy (1 processor + 1 GB) for a full month = $0.000011244 × 2,628,000 s + $0.000001235 × 2,628,000 s = $32.80, less the free allowance worth $5.22. Wake-per-film = $0.000024 + $0.0000025 per second while a film is being made. That is about $0.0008 per 30-second film, or $0.80 per 1,000 films. The free allowance (180,000 processor-seconds a month) covers about 6,000 films. Sending films out of Google: the first 1 GB a month is free, then $0.12 per GB. 1,000 films × ~5 MB = ~5 GB, so about $0.48. One flag: Google's own worked example on that page prices an always-on copy lower ($16.83) than its own price table gives. Even the lower figure costs more than Render's $7.

My recommendation

Option B: the film server wakes up for each film

$0 / month now · about $0.50 at 1,000 films

It saves the $14 a month you pay Render. It stays near free after the Google credits end. It also handles a rush of films on its own, because every film gets its own copy. Option A costs more than Render, so it isn't worth moving for.

The brief suggested a Google "job" for this. I recommend a Google "service" that sleeps instead. A job is meant for long one-off work, like the explainer renders, and takes longer to start. A sleeping service starts in seconds and is billed only while a film is being made. I haven't measured either start time yet. Google signed this Mac out overnight, so I couldn't read the explainer's start times. I will measure both before anything goes live.

The rule I'll hold it to: the middle film must finish within 5 seconds of today's 22 s. If it doesn't, the fix is to keep one copy awake. That costs about $13 a month, which is still less than Render. I'd ask you before doing that.

Safety

Keys, stuck films and alerts

  • Keys: the server needs only one secret, the database key. It goes in Google Secret Manager, readable only by the film server's own Google account. No key files (your company setting blocks them anyway). The server needs no R2 keys. Each film comes with its own one-time upload link.
  • A server that dies mid-film: today another copy picks the film up after 3 silent minutes. With option B, a safety check every minute wakes the server if a film is waiting or stalled. So a dead server's film restarts within about 4 minutes, and the customer is never charged twice. This uses the timer that already runs every minute for Google videos.
  • Alerts: one correction to the brief. A Telegram alert for a stuck queue already exists. It messages you when a film waits more than 5 minutes, and again when films flow again. It also alerts when the server's "still alive" signal stops. With option B the server sleeps between films, so that "still alive" signal would false-alarm. I'd change it to alert only when a real film isn't picked up. I'd test it by staging a stuck film and confirming the message reaches you.
