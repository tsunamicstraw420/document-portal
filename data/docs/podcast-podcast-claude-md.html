STOP — READ BEFORE DOING ANYTHING

These exist because ignoring them cost Eddie a full day (Aug 6-7 2026). They are not suggestions. Read them at the START of every session, and again before choosing HOW to do any operation.

0. NO IMPROVISING — EVER. FOLLOW THE DOCUMENT, EXACTLY. When an assembly/plan document exists (EDIT_TIMELINE, ANIM_WORKLIST, CAPTIONS_PLAN, a shot list, a beat sheet), build beat-by-beat to that document. Do NOT remap its numbering, substitute clips, merge beats, invent placements, or "adapt" it on the fly. If the document is stale, wrong, or conflicts with another document: STOP. Update the document first, get Eddie's sign-off on the corrected document, THEN build strictly to it. A build that does not match the document is a FAILED build even if it imports and plays. Document first, build second — the build is a transcription of the document, never an improvisation. (This rule cost a full day of timeline rebuilds on EP11, Aug 15 2026: I wrote the EDIT_TIMELINE, then threw it out and improvised a hybrid instead of building to it.)

1. Copy the working example. Never design a new approach. If this project has done this kind of operation before - publishing, building, pushing, converting - find how it was done and do it that way. Read the prior script, folder, or memory FIRST, before forming a theory. Improvising a "better" method is the single most expensive mistake made on this project. A boring path that works beats a clever path that half-works.

2. Route order. Never skip down this list.

  1. A connector / MCP tool that does the job directly
  2. Re-attaching a source or reconnecting a connector so that tool CAN do it
  3. device_bash (Eddie's files, no network) or Bash (cloud, has network)
  4. A .command file Eddie double-clicks once and walks away from
  5. Claude in Chrome - LAST RESORT. It pins his laptop so he cannot work, and forces

him to sit and watch. Before proposing it, state which of 1-4 were tried and the exact error each gave.

3. Do not ask Eddie for clicks until every other route has actually been tested. Not "I think this is blocked" - tested, with the error message in hand.

4. Never make him sit and watch. He multitasks. Any approach that occupies his machine or needs his supervision is a failed approach, even if it eventually works.

5. Verify before handing back. Run every check, report the numbers. Never hand him QA.

6. When something does go wrong, fix the cause, not the instance. Write the working method down so the next session inherits it instead of rediscovering it.

7. Never write files with shell heredocs. Use the Write/Edit tools or the Filesystem MCP. A heredoc silently wrote EOF and a raw cat line into another project's CLAUDE.md and it sat there undetected for months.

**8. Never open, echo, or edit Accounts_info.rtf, kling.kling_key.rtf, or any _creds/.key file.** Read only when the task requires it; never into chat.

  • EP-02: skipped Kara & Guillermo in the recap, requiring a re-record. **Rule: cast

  • **2026-08-11: transitions wouldn't stick — every clip was rendered to its exact visible

length, so it had zero handles, and DaVinci dipped to black / threw "insufficient handles" at every cut. I also wrongly told Eddie the "seamless" pack needed no handles (its own tutorial just uses normal footage that already has them). Rule: any clip destined for a timeline gets ≥1s of handle padded onto EACH end (ffmpeg tpad=start_mode=clone:start_duration=1:stop_mode=clone:stop_duration=1), and it is placed with in/out offset by the pad so the visible cut and A/V sync are unchanged. Never hand over a timeline of exact-length clips when transitions are coming — no transition, seamless or not, works without handles.**

  • 2026-08-12: caption + Shorts drift. Everything was timed from the RAW narration word-JSON,

but the master's audio is edited/trimmed after recording, so timings drifted 1.6s→8s — the YouTube master's burned karaoke AND all 10 Shorts were mistimed (clipped opening words, captions 2–8s off). Root cause: wrong source of truth. Rule: build captions AND Shorts clip-windows from a transcript of the FINAL exported master's OWN audio (Whisper the master → lipsync/<ep>.MASTER_words.json), never the raw-narration JSON. Cut with frame-accurate two-stage seeking (-ss before AND after -i) so no opening word is clipped, and verify by transcribing each output's first ~3s before handing back. Also group karaoke lines to break on pauses (>~0.7s gap between words) and cap line length (~3.2s), so a line spanning one of Ruby's dramatic pauses can't show its later words before they're spoken. Verify DENSELY across the whole runtime (every ~30s), not just 2–3 spots — a 3-point check missed a bad 6:19 pause once.

  • 2026-08-12 (later): wasted a whole session handing Eddie repeated failed .command runs

instead of the boring reliable thing. The sandbox (where captions normally burn, because its ffmpeg HAS libass) was down, so I moved the burn onto Eddie's Mac WITHOUT first checking his ffmpeg — then shipped three broken runs: (1) -v error hid the real ffmpeg error; (2) his newer Mac ffmpeg rejects the bare subtitles=FILE:… shorthand; (3) his /usr/local/bin/ffmpeg has NO libass at all, so it physically cannot burn .ass. Rules: (a) Before handing over ANY render that runs on the Mac instead of the sandbox, confirm the Mac tool can actually do it — the Mac's ffmpeg has no libass. Use EP05_S3E5/run_ep05_rerender.command, which auto-acquires a caption-capable ffmpeg (checks every local ffmpeg → brew → static download) and burns/renders locally; reuse that pattern, don't reinvent. (b) Caption filters are ALWAYS subtitles=filename=…:fontsdir=… and ass=filename=…:fontsdir=… — the bare form breaks on the Mac. (c) Never render with -v error when it might fail; keep full ffmpeg stderr in the log so the cause is visible on the first try. (d) When the sandbox is down, that IS the blocker — either wait for it or go straight to a Mac-local method that accounts for the Mac's tools; do not improvise piecemeal and turn Eddie into the debugger.

  • **2026-08-13: the EP05 YouTube re-burn came out with karaoke captions ~2s AHEAD of the

audio in every chunk EXCEPT chunk 0. Root cause: burn_youtube_ep05.py's _seek() used a two-stage seek (-ss t0-2 -i SRC -ss 2). The subtitles filter reads frame PTS that reset to 0 at the seek point, so the shifted .ass got drawn ~2s early wherever the pre-roll was 2s — i.e. every chunk but chunk 0, whose pre-roll is 0 (that's why chunk 0 alone looked aligned). The .ass was correct (matched MASTER_words to the word); the RENDER shifted it. Fixes: (a) _seek() now does a pure input seek (-ss t0 -i SRC), frame-accurate on modern ffmpeg, so every chunk aligns like chunk 0 — verified: frame @50s read "SHE KIND OF WORDS…" (wrong, +2s) before, "OF PATRICK." (correct) after. (b) Verify the BURNED PIXELS, not just the .ass: extract real frames across the whole runtime and confirm the GOLD karaoke word matches the spoken word at that second. The .ass-vs-MASTER_words table will look perfect even when the burn is 2s off, because both sides come from the same source — only a pixel read catches a render-timing shift.**

Hard constraints

Non-negotiable. Violating one of these means redoing work.

  • Episode length: 15 MINUTES MAXIMUM (Eddie, July 20 2026). Scripts must be written

to land under 15 min after narration, not trimmed afterwards. EP-02 came in at 19:05 after already cutting 88 seconds. Shorter also means fewer shots to generate and review, which is the real production cost.

  • Cover EVERY cast couple/member of the show being recapped. Never skip one. Verify

against the manifest before finalizing.

  • No Microsoft products. Always PDF — never DOCX, XLSX, or PPTX.
  • One folder per published episode — everything uploadable lives together. Every file

that gets uploaded/published for an episode — the YouTube video, the Spotify master, the caption .srt, the Shorts, AND the upload pack doc — must live in that episode's _READY_TO_UPLOAD/<EP>/ folder. Never leave an upload asset only in the workshop folder or a buried subfolder like captions/ (the EP05 .srt hid in captions/ and Eddie couldn't find it, Aug 12 2026). Shorts may sit in a clearly-named Shorts/ subfolder inside it. Opening _READY_TO_UPLOAD/<EP>/ must show everything needed to publish, with nothing to go hunting for.

  • Captions are LOCKED (full detail in each episode's CAPTIONS_PLAN.md):
  • Built from our OWN word-level transcript (lipsync/*_CLEAN.words.json), never YouTube.
  • YouTube video = karaoke captions BURNED IN and upload the plain .srt too

(for search).

  • Spotify video = CLEAN. No burned captions, and do not upload the SRT — Spotify

auto-captions.

  • Shorts = their own vertical karaoke burned in, always cut from the CLEAN master,

never from the burned YouTube file.

  • Long-form karaoke style is locked: Bangers 120, spoken word gold. Do NOT revert

long-form to switchable-SRT-only — that was the pre-EP-04 approach.

  • Transcript source = YouTube (June 2026). Upload unlisted first, pull YouTube's

auto-generated transcript via Chrome, use it for show notes, description, and chapters. Not for captions — see above.

  • Teleprompter derivation: strip production notes, headers, dividers, and timing;

keep spoken words, [delivery tags], and */*** pause markers. Teleprompter Docs live in the podcast Google Drive "Video scripts" folder. See the project_teleprompter_scripts_setup memory.

  • Production pipeline = Ruby → Magnific → Resolve. Ruby records the voice; the Magnific

process turns that recording into the show (animated Ruby lip-sync + scene visuals); everything out of Magnific goes into DaVinci Resolve for editing/assembly, then export. We do NOT use Riverside — do not reintroduce it. Shorts are cut from the exported master by timecode (EP##/shorts_pipeline/make_shorts.py), not by any auto-clipper.

  • Notion: only the Episode Tracker is auto-populated (Zap #1). Content Calendar

and Show Notes Library are written directly by Claude — they are NOT event-triggered Zaps. Don't go looking for a Zap that doesn't exist.
