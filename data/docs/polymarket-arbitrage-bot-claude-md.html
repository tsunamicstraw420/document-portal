Polymarket Arbitrage Bot — Project Context

This file is project-specific context. Read it before doing anything on this codebase.

Operating principle: stop guessing, always double-check

Before asserting any fact, check it. Before claiming a tool or capability isn't available, list what's actually loaded. Before claiming a server is production, check what's running on it.

Why: This rule comes from two close-spaced failures on 2026-05-10:

  1. Deployed v1.7 to Jakarta because DEBUG_REPORT.md said Jakarta was production. The real production server (London at the time) had been running for 4 days; the assertion in the doc was stale. Should have run docker compose ps on both servers before touching anything.
  2. Told the user I "couldn't" change a Hostinger VPS location via SSH and that they had to do it in hPanel — without checking that Chrome MCP tools were loaded and could in fact drive hPanel.

How to apply:

  • "Where is X running?" → ssh && docker ps, not "the docs say…"
  • "Can I do X?" → list available tools / try a no-op first, not "I don't have access to that"
  • "What version of Y is in production?" → docker compose exec ... grep ..., not "the latest commit"
  • "Is this safe?" → cross-check the actual on-disk / on-server state, not the most recent thing said in chat
  • Stale docs are a known failure mode in this codebase. Live state always wins over written claims, including this file.

Operating principle: the bot log is intent, not outcome

Trading-bot ground-truth rule: Before any claim about whether trades did or didn't happen, fills landed, PnL is real, or balance moved — cross-check the wallet or Polymarket's REST API. The bot's log records what the bot THINKS happened. It is not evidence of what actually executed on-chain.

Why: On 2026-05-13 I claimed "47 GTC orders, all no-fills, zero trades" based solely on the bot's log. The wallet's actual Polymarket activity history showed 4 successful BUYs filling for ~$23 USDC that day, two of which resolved profitably for ~$41 in payouts — net +$18.23. The bot mis-reported because there's a race condition between its 5-second cancel + get_order query and Polymarket's matching engine: orders that match late are recorded as size_matched=0 at query time, then actually fill seconds later. The bot's _live_positions and trades.db have been chronically out of sync with the wallet for weeks.

Sources of truth for THIS bot, in order of authority:

  1. Wallet balance and on-chain Polygon transactions (immutable)
  2. Polymarket's activity / positions / trades REST endpoints
  3. The user's downloaded Polymarket CSV
  4. The bot's data/logs/bot.log — only as a hint about intent, never as proof of outcome

Mandatory checks before stating outcomes:

  • "The bot made X trades" → fetch from Polymarket activity API
  • "Fills aren't landing" → cross-check wallet balance change and Polymarket positions
  • "PnL is N" → derive from wallet, not from STATUS log lines
  • "Position closed" → confirm via Polymarket's /positions (current) or /trades (history)

Operating principle: name your source

When making a state claim, explicitly name the source you checked. "The bot log shows X" is fine. "X is happening" without naming a source is forbidden when X is empirically verifiable. The phrasing forces the discipline.

Operating principle: when an answer depends on two sources, check both before recommending

If the right answer requires data from sources A and B, do not produce a recommendation from A alone. The correct shape is: "A says X; B says Y; therefore Z" — OR — "A says X but I haven't checked B yet; let me verify before recommending."

This rule exists because confident wrong recommendations have cost real money and real time on this codebase. The CLAUDE.md "stop guessing" rule alone was not enough. This is its operational form: a checklist that fires per recommendation.

Operating principle: empirical testing trumps documentation reading every time

When an API or upstream service's behavior is in question, write a 50-line probe and run it. Don't rely on docs, README summaries, or what a WebFetch told you the source code says. Production behavior is the only source of truth.

Why: This rule comes from the 2026-05-11 Chainlink RTDS investigation. I'd repeatedly claimed (and shipped) Chainlink subscribe code based on:

  1. A WebFetch summary of Polymarket's README (correct topic name, wrong filter shape)
  2. Historical git commits' assertions ("Chainlink ticks are sparse" — wrong, my filter was rejecting them)
  3. My own pattern-matching from the SELL FAK code (right shape, wrong field semantics)

Each of those felt like "double-checking." None of them were. The real test took ~2 minutes: a standalone probe script that tried 4 subscribe variants for 30 seconds each and counted frames. It immediately revealed (a) the bot's current config received 0 Chainlink frames, (b) empty-filter received 189 frames in 30s, and (c) the supposed-correct filter format silently delivered nothing.

How to apply:

  • "Does this API do X?" → write a probe and call it. Don't ask another LLM to summarize the docs.
  • "Are messages flowing on this WebSocket?" → connect and count frames. Don't trust counts from logs that were generated by code you suspect is broken.
  • "Will this order type fill?" → place ONE tiny order with a 30-second cooldown. The CSV of real fills is the only evidence that counts.
  • A 50-line probe script that proves the actual behavior is worth more than a 1000-line analysis based on documentation.
  • "Documentation reading" includes: WebFetch results, README summaries from search engines, GitHub issue summaries, and even your own prior conclusions. None of them are the live API.

What this bot does

Latency arbitrage between Binance BTC/ETH price moves and Polymarket "Up or Down" 5-min / 15-min binary markets. The edge is speed — detecting a Binance move before the Polymarket CLOB reprices. Every decision is in service of latency. Don't add anything to the hot path (signal → decision → order) without a clear latency win.

Two strategy paths, dispatched per-market by how far through the window we are:

  • Binance-momentum (0–70% through window): Predict direction from a recent Binance move. Uses logistic true_prob + Kelly sizing + 5% edge threshold.
  • Chainlink-settle (70–100% through window): Observe where Polymarket's Chainlink Data Stream currently sits vs. the window-open price. Bet the side already winning — Polymarket settles on the Chainlink price at window close. 3% edge threshold (higher conviction = lower bar).

Critical invariants

  • Only ONE bot may run at a time — all instances share the same Polymarket wallet, so running two = double trades. The whole point of decommissioning Jakarta was to remove this footgun. If a future server is ever added (Amsterdam standby, etc.), this rule applies.

Deploy workflow — git only, NEVER scp

The bot source is git-managed. NEVER scp source files directly to /opt/polymarket-bot/ — they'll be overwritten on the next git pull. This mistake was made on 2026-05-10; don't repeat it.

# On Mac
cd /Users/rubys/Desktop/AI_bots/Polymarket-Arbitrage-Bot
git add <files>
git commit -m "describe change"
git push origin main

# On Vilnius (one-liner)
ssh poly-vilnius "cd /opt/polymarket-bot && git pull && docker compose build polymarket-bot && docker compose up -d polymarket-bot"

Hard rules

  • NEVER docker compose up --force-recreate — Docker network namespace teardown breaks Binance WS startup. Plain docker compose up -d picks up the new image correctly.
  • NEVER push to main without explicit user confirmation (the harness blocks it by default; ask first).
  • .env is not in git — scp is the only way to update it on a server.
  • .git/ is rebuildable from origin; data dir (.env, state, positions, trades.db, logs) is not — back it up before any server-destructive operation. Local backups live in vps_data/, gitignored.

Monitoring — no SSH for normal observation

  • Telegram heartbeat every 30 min. If you don't see one for 60+ min, something's wrong.
  • Dashboard: http://76.13.78.74 (always-on WebSocket).
  • SSH is for deploys and debugging only. Don't sit on tail -f for monitoring.

Price feeds

The bot subscribes to two WebSockets:

  1. Binance (wss://stream.binance.com:443/stream) — btcusdt@miniTicker, ethusdt@miniTicker. Drives the Binance-momentum strategy. Auto-reconnects with backoff.
  2. Polymarket RTDS (wss://ws-live-data.polymarket.com) — same Chainlink Data Stream Polymarket uses to settle crypto markets. Drives the Chainlink-settle strategy. Sends app-level PING every 5s to maintain connection.

RTDS subscribe message format (matches the official Polymarket/real-time-data-client TS library):

{
  "action": "subscribe",
  "subscriptions": [
    {"topic": "crypto_prices_chainlink", "type": "update", "filters": "{\"symbol\":\"BTCUSDT\"}"},
    {"topic": "crypto_prices_chainlink", "type": "update", "filters": "{\"symbol\":\"ETHUSDT\"}"}
  ]
}

Chainlink live updates are observed to be sparse (likely on-chain heartbeat cadence). CL:stale in feed_status is normal; the Chainlink-settle strategy is a graceful no-op when no recent data. Investigation of gamma_auth for denser delivery is a future task.

Strategy parameters worth remembering

Binance-momentum

ParamValueWhy
EDGE_THRESHOLD_BY_DURATION{5: 0.04, 15: 0.03}Per-duration edge floor: 5-min markets need 4% edge, 15-min need 3% (15-min is statistically less noisy)
EDGE_THRESHOLD0.05 (5%)Fallback for any duration not in the map above
MIN_PRICE_MOVE_PCT0.0007 (0.07%)First-gate filter — but real signal bar is ~0.27% because of true_prob >= 0.60 with k=150
MAX_PRE_ENTRY_SEC30Don't enter more than 30s before window opens
MOMENTUM_CONFIRM_SEC10Short-window confirmation of the 30s signal (renamed from MOMENTUM_LOOKBACK_SEC — it's a check, not a time gate)
_MOMENTUM_TOLERANCE0.0002 (v1.7)Allow 0.02% drift against signal before blocking — strict >0 was killing post-spike signals
_TICK_BUFFER3000 (v1.7)Was 400 — too small for the previous relay's tick rate

Chainlink-settle

ParamValueWhy
CHAINLINK_LATE_ENTRY_PCT0.70Switch from Binance to Chainlink at 70% through window
CHAINLINK_EDGE_THRESHOLD0.03 (3%)Lower than Binance's 5% — conviction is higher when observing current direction vs. predicting future
CHAINLINK_MIN_DELTA0.0010 (0.10%)Require ≥0.10% Chainlink delta from window-open to avoid flip-prone resolutions
CHAINLINK_SCALE_FACTOR200.0Sigmoid steepness on (delta × time_progress)

The true 5-min Binance signal floor is 0.27% over 30s (where true_prob crosses 0.60), not the 0.07% the config suggests. NEAR-MISS logs (v1.7+) make the 0.07%-0.27% silent zone visible: NEAR-MISS BTC DOWN 5min | move=-0.086% true_prob=0.532 edge=1.21% (need 5%).

Self-correcting workflow (hooks in .claude/)

Automatic guardrails defined in .claude/settings.json:

  • After every .py write/edit: syntax-checked with py_compile; any error is fed straight back to fix in the same turn.
  • Before any write to .env: blocked (it holds live keys/wallet secrets); .env.example is allowed.
  • When Claude says it's done: every top-level .py must still compile or work continues. (Swap to pytest here once tests exist.)

Keep this file self-correcting: whenever the user corrects a real mistake, append it to the numbered list below and end with "Update CLAUDE.md so you don't make that mistake again."

Things that have gone wrong (so we don't repeat them)

  1. 2026-05-10: deployed v1.7 fixes to Jakarta instead of London because DEBUG_REPORT.md referenced Jakarta as production. Started a duplicate bot on the same wallet for ~18 min. No actual trades fired during the overlap. Fixed by stopping Jakarta and redeploying via the git workflow.
  2. 2026-05-10: claimed Hostinger VPS location change was "no downtime / no data loss" based on a 2023 third-party article. The actual in-place change WIPES the VPS. Caught before clicking confirm — but only because the hPanel dialog itself warned. Verify Hostinger-specific behavior with Hostinger sources, not blog posts.
  3. 2026-05-10: my first Polymarket RTDS subscribe format was wrong ("Invalid request body" from the server). The correct shape (subscriptions: [{topic, type, filters}]) came from the official Polymarket TS client repo, not from the docs page. When subscribing to AWS API Gateway WebSockets, find a working client and copy its format — don't guess.
  4. 2026-05-10: a single echo >> authorized_keys on a fresh VPS concatenated my key onto the previous line because the file didn't end with a newline. Future fix: use cat >> ... <<EOF with a literal trailing newline, or printf '\n%s\n'.
  5. 2026-05-30: read and edited the codebase from a local checkout that was 28 commits behind origin/main. Spent a whole session designing a multi-asset change against stale versions of config.py, market_scanner.py, bot.py, strategy.py — the gate logic I edited had already been rewritten on the remote (and on the live VPS). Only caught it when git push was rejected as non-fast-forward. Always git fetch origin && git log --oneline origin/main..HEAD HEAD..origin/main at the START of any code work on this repo — the live bot tracks origin/main, not whatever the Mac last had. Live state wins over local, same as the top-of-file rule. Recovery: stash protected uncommitted files (CLAUDE.md, BotSettings.txt — confirmed not changed on remote first), git reset --hard origin/main, re-apply edits against current code.
  6. 2026-05-30: deploy "succeeded" but silently saw only ~20 of ~50 markets. Polymarket's Gamma /events endpoint defaults to a 20-event page. BTC/ETH (≈20 slugs) fit under the cap by luck; adding SOL/XRP/BNB (≈50 slugs) truncated the response to an arbitrary 20. Would have run a half-blind bot if I'd trusted the green "deployed" signal. After any change that grows the number of scanned markets, verify the live active-market count, don't assume. Fixed by passing limit=max(len(slugs),100) on the fetch (commit 9d46fc7).
