Root Cause Summary

Four issues identified, in priority order:

Bug #1 — Momentum check is over-blocking (PRIMARY CULPRIT)

File: strategy.py line 183–185

# CURRENT (broken):
signal_is_up = price_change > 0
still_moving = move_10s > 0 if signal_is_up else move_10s < 0
if not still_moving:
    return None

Problem: The strict > 0 / < 0 means the signal is killed the instant BTC stops accelerating — even at 0.000%, even for a single 0.5s scan. In practice: BTC spikes → price plateaus at new level → move_10s = 0.000% → 0.000 > 0 is False → signal blocked. This kills signals for the entire duration of a consolidation (which is often most of the 5-min window after a spike). The log says "Momentum block" at DEBUG level — totally invisible in INFO logs.

Fix:

# FIXED — allow up to 0.02% drift against trend before blocking
_MOMENTUM_TOLERANCE = 0.0002
still_moving = move_10s > -_MOMENTUM_TOLERANCE if signal_is_up else move_10s < _MOMENTUM_TOLERANCE

Bug #2 — Tokyo relay overflows the tick buffer

File: price_feed.py line 24

# CURRENT (broken for relay use):
_TICK_BUFFER = 400  # ~6-7 min at ~1 tick/s

Problem: The buffer was sized for Binance miniTicker (1 tick/s). The Tokyo relay (signal_relay.py) streams Binance aggTrade events at 10–50 ticks/second for BTC. At 20 aggTrades/s, the 400-tick buffer only covers ~20 seconds of history. When price_change_pct(lookback_sec=30) is called, it can only look back 20s because that's all that's in the buffer. A sustained +0.30% drift over 30s only shows as +0.15% over the effective 20s window — below the 0.27% threshold needed to clear the 60% true_prob floor. This specifically hurts gradual sustained moves (as opposed to flash spikes), which is exactly the pattern that should be the easiest to trade.

Fix:

# FIXED — supports relay at 50+ aggTrades/s with full 30s coverage
_TICK_BUFFER = 3000  # ~60s at 50 ticks/s, ~50 min at 1 tick/s

Design Issue #3 — 60-second dead zone every 5 minutes (silent)

Files: strategy.py, config.py

Problem: The combination of:

  • MAX_PRE_ENTRY_SEC = 30 (don't enter more than 30s before window opens)
  • MIN_ENTRY_SECS_REMAINING_5MIN = 90 (block if <90s remain = block after T+210s)

...creates a 60-second gap every 5 minutes (from T+210s to T+270s) where no 5-min entry can fire. In a 35-minute window: 7 gaps × 60s = 7 minutes of total dead time. All of this is silent — no log output at INFO level.

Timeline per window:

T-30s  → pre-entry opens (MAX_PRE_ENTRY_SEC)
T+0s   → window opens
T+210s → entry closes (MIN_ENTRY_SECS_REMAINING_5MIN = 90s before T+300)
         ← 60-second gap — NO ENTRY POSSIBLE →
T+270s → next window's pre-entry opens (30s before T+300)
T+300s → next window opens

Fix (optional): Reduce MIN_ENTRY_SECS_REMAINING_5MIN from 90 to 60, which shortens the dead zone from 60s to 30s. Alternatively, add a INFO-level log when a signal is blocked by the time gate so you can see it happening.

Design Issue #4 — True signal bar is 0.27%, not 0.07% (misleading config)

Files: config.py, strategy.py

Problem: MIN_PRICE_MOVE_PCT = 0.0007 (0.07%) looks like the entry bar, but the actual effective minimum is 0.27% — the move needed for true_prob ≥ 60% with k=150 (5-min steepness). Any Binance move between 0.07% and 0.27% passes the first gate, looks like it's being evaluated, and then fails silently at the edge/probability check. There are zero INFO-level logs for this failure mode.

Math:

prob_up = 1 / (1 + exp(-150 × price_change_pct))
For prob_up ≥ 0.60: price_change_pct ≥ ln(0.60/0.40) / 150 = 0.270%
For prob_up ≥ 0.70: price_change_pct ≥ 0.438%
For prob_up ≥ 0.80: price_change_pct ≥ 0.693%

Moves in the April 18 13:10–13:45 PT window peaked at 0.076% for BTC — legitimately below the effective threshold. The bot was correct to not fire. But if the user saw a move they expected to qualify, they may have been looking at a 5-minute candle move rather than a 30-second rolling Δ.
